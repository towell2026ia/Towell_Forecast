# PRD 09.2B — Reconciliación legacy y gate de esquema

Fuente de verdad: [PRD 09.2A](PRD09_2A_SUPABASE_DATA_CONTRACT.md). Esta auditoría clasifica objetos SQL, **no datos**. Los seis archivos históricos se conservaron intactos en `supabase/legacy_migrations/`. Ningún objeto legacy se considera seguro para ejecutar sobre el proyecto nuevo sólo por existir en Git.

## Estado remoto y decisión de aplicación

Proyecto vinculado: `bskoyqhbgrycpwhydnnr` (`Towell_Forecast`). `supabase migration list --linked` muestra **cero migraciones remotas**: las seis legacy estaban sólo en local. Un `SELECT` de `information_schema.tables` muestra **cero tablas/vistas en `public`**; únicamente existen tablas gestionadas por Supabase en `auth`, `storage`, `realtime`, `vault`, etc. Otro `SELECT` confirma los schemas `auth`, `extensions`, `graphql`, `graphql_public`, `public`, `realtime`, `storage`, `vault`. `supabase inspect db table-stats --linked` devuelve cero tablas de aplicación. No se extrajeron filas de negocio. `supabase db dump --schema public` no pudo ejecutarse porque Docker/Podman no están instalados; la inspección por catálogo cubrió el inventario requerido. Ningún SQL de cambio se ejecutó en remoto.

La CLI está fijada como dependencia de desarrollo `supabase@^2.118.0`. Con el remoto vacío confirmado, las seis migraciones legacy se archivaron localmente **sin alterar su contenido** y las cuatro nuevas se colocaron en `supabase/migrations/` para poder revisar `db push --dry-run`. Esto no aplica SQL remoto ni conecta el runtime.

`npx supabase db push --dry-run --skip-vault --linked` terminó con código 0 y listó **únicamente** `202609250001_contract_core.sql`, `202609250002_contract_forecast.sql`, `202609250003_contract_governance.sql` y `202609250004_contract_integrity.sql`. La CLI indicó expresamente que no las aplicó. Los seis SQL legacy conservaron exactamente los mismos hashes Git que en `HEAD` antes de moverlos.

Una comprobación read-only **posterior** al dry-run devolvió `403`: la CLI volvió a mostrar una sesión de otra cuenta que no tiene acceso al proyecto objetivo. Esto no cambia el inventario y dry-run exitosos obtenidos con la cuenta autorizada, pero impide certificar una segunda lectura posterior. Antes de cualquier push real debe reautenticarse la cuenta correcta y repetir las comprobaciones; no se usarán credenciales de la cuenta ajena.

## Significado de la matriz

- **KEEP**: DDL físico compatible sin cambio. Resultado: **ninguno**; los archivos se preservan sólo como evidencia Git.
- **TRANSFORM**: concepto/data lineage aprovechable, pero requiere tabla/clave/función nueva.
- **REPLACE**: función todavía necesaria, implementación legacy incompatible.
- **RETIRE**: no pertenece al contrato 09.2A o supone autoridad/política insegura; no se crea en el baseline.

Las FK son restrictivas; no hay borrado en cascada de historia.

## Riesgos y decisiones pendientes antes de aplicar SQL remoto

1. **Cambio externo/sesión CLI entre auditoría y aprobación.** La historia remota y `public` estaban vacíos al auditar, pero la segunda lectura encontró una cuenta distinta y fue denegada. Antes de un push aprobado habrá que reautenticar la cuenta correcta y repetir `migration list` y el inventario de `public`; cualquier objeto nuevo reabre la reconciliación. Los seis archivos legacy ya están fuera de `supabase/migrations/` y preservados por Git.
2. **09.2C pendiente.** RLS está activado y sin políticas de usuario: seguro por defecto, pero ninguna operación del navegador funcionará hasta revisar Auth/RLS/Storage. `public.users` y los permisos legacy no se trasladan.
3. **Ingesta y cutover pendientes.** `uploaded_at` debe sellarlo el backend en 09.2D; sólo el rol de servicio puede insertar mientras RLS está cerrado. El SQL rechaza fechas de disponibilidad inconsistentes y no infiere fechas históricas. E1/E2/E3 requieren evidencia validada y ruta de manifiesto. Históricos `UNKNOWN` permanecen sin `available_at`.
4. **Snapshot de categoría.** `forecast_horizons.category_id` guarda la categoría al crear el pronóstico para evitar que un cambio futuro de catálogo reescriba la lectura de agregados congelados.
5. **Roles de servicio.** Las funciones de integridad son triggers internos; permisos de ejecución y políticas se endurecerán en 09.2C. El baseline no implementa aún `ChampionRegistry.publish()` ni expone escritura de Champion al usuario final.
6. **Prueba local vs. remoto.** PGlite ejecuta el SQL y prueba constraints, pero no demuestra compatibilidad con la configuración exacta del proyecto Supabase ni restauración real. La revisión de dry-run y una aprobación explícita siguen obligatorias.
